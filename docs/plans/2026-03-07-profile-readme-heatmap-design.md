# GitHub Profile README 精简与贡献热力图自动化设计

**日期：** 2026-03-07  
**状态：** 已确认设计  
**适用仓库：** `axin7`

---

## 1. 背景与问题

当前仓库本质上是 GitHub Profile README 仓库，但首页承担了过多职责：

- 同时在做个人介绍、项目导航、理念表达
- `Anyveo` 子项目展开过多，视觉重心偏向“项目列表”
- 自我介绍与方法论存在重复表达
- 页面缺少动态内容，无法持续体现“活跃度”和“正在建设中”的状态

用户目标已经明确为：

1. 主页首先突出“你是谁”
2. 同时保留独立开发者气质与方法论表达
3. 展示层每天自动更新真实 GitHub 贡献图表
4. 不采用伪造贡献数据或单纯刷 commit 的方式

---

## 2. 设计目标

本次重构后的仓库只承担两类职责：

1. **个人名片**：让访问者在 10 秒内知道你是谁、做什么、价值判断是什么
2. **动态展示**：通过 GitHub GraphQL API 拉取真实贡献数据，自动生成更美观的热力图展示

不再承担完整项目黄页职责。项目矩阵信息应收缩为少量精选入口。

---

## 3. 信息架构

建议将首页重构为 4 个固定区块：

### 3.1 Hero / 个人定位

承载：
- 名字
- 一句话定位
- 身份与城市
- 2～3 个高价值关键词

目标：
- 访问者第一眼先记住“Feng Xin 是谁”

### 3.2 How I Think / 方法论

承载：
- 你如何理解 AI 产品
- 为什么偏好 calm AI tools
- 对长期主义、真实场景、低打扰工具的偏好

目标：
- 强化独立开发者气质，而不是堆叠履历

### 3.3 Selected Work / 精选入口

保留 2～3 个入口：
- `fengxin.me`
- `Anyveo`
- 1 个代表性方向或产品入口

目标：
- 从“项目大全”收缩为“精选入口”

### 3.4 Activity / 自动更新区

承载：
- 自定义贡献热力图 `assets/heatmap.svg`
- 后续可扩展的统计摘要 `assets/stats.svg`

目标：
- 让页面持续变化，同时基于真实数据保持可信度

---

## 4. 技术架构

建议目录职责如下：

```text
README.md                 # 最终展示层
assets/                   # workflow 生成的 SVG 图表
scripts/                  # GitHub 数据抓取与 SVG 生成脚本
.github/workflows/        # 定时更新任务
```

分层原则：
- `README.md` 只负责展示和引用生成结果
- 图表逻辑全部放在 `scripts/`
- 自动化调度全部放在 `.github/workflows/`
- 生成产物统一放在 `assets/`

这样可以保证：
- 展示层稳定
- 自动化逻辑集中
- 后续样式和文案修改互不干扰

---

## 5. 数据源与生成方案

### 5.1 数据源

唯一推荐数据源：**GitHub GraphQL API**。

核心原因：
- 可以直接查询 `contributionsCollection`
- 数据结构天然适合构建热力图
- 能同时支持年度统计、按周数据、按日强度数据

本次 MVP 重点使用：
- `ContributionCalendar`
- `ContributionCalendarWeek`
- `ContributionCalendarDay`

### 5.2 生成产物

MVP 阶段先生成：
- `assets/heatmap.svg`

后续扩展可增加：
- `assets/stats.svg`
- `data/contributions.json`

### 5.3 脚本组织

优先采用**单脚本方案**：

```text
scripts/generate_github_heatmap.py
```

该脚本负责：
- 拉取 GraphQL 数据
- 标准化贡献日历
- 渲染 SVG 文件
- 写入 `assets/heatmap.svg`

这样做更符合当前仓库体量，避免过度工程化。

---

## 6. Workflow 设计

推荐保留两个触发器：

- `schedule`：每天定时执行
- `workflow_dispatch`：支持手动立即执行

执行流程：
1. checkout 仓库
2. 安装 Python 运行环境
3. 调用脚本拉取贡献数据并生成 SVG
4. 校验生成文件有效性
5. 仅在文件变化时提交更新
6. push 回默认分支

稳定性原则：
- 失败时不覆盖旧文件
- 没有变化时不提交
- `README.md` 只引用结果，不参与逻辑计算

---

## 7. 视觉风格方向

图表风格应与主页气质保持一致：

- 低饱和配色
- 偏 calm / durable / professional
- 适合 GitHub README 的浅色背景
- 不做夸张渐变或竞技型视觉
- 保留适度留白与圆角感

一句话方向：

> 像一个克制、长期主义的独立开发者主页，而不是“刷榜型”数据面板。

---

## 8. README 重构原则

### 保留
- 名字与定位
- 方法论
- 精选入口
- Activity 区块

### 删除或收缩
- 详细项目矩阵
- 冗余双语重复段落
- 过长联系方式列表
- 项目型说明文字的大段铺陈

文案风格：
- 中文主导
- 短句表达
- 重点突出“你本人”而非“全部项目”

---

## 9. 验收标准

重构完成后，应满足以下标准：

1. 打开主页 10 秒内能明确知道你是谁
2. 首页不再呈现“项目大全”感
3. `README.md` 稳定展示自定义贡献热力图
4. GitHub Actions 可手动触发并成功更新
5. 定时任务可按日自动刷新
6. 任务失败时页面仍展示上一次成功生成的图表

---

## 10. 范围边界

本次设计**不包含**以下内容：

- 修改 GitHub 官方原生贡献格子的样式
- 伪造贡献数据
- 通过空提交或刷提交制造活跃度
- 构建完整 GitHub Pages 站点
- 在本次 MVP 中引入过多外部依赖

---

## 11. 最终结论

本次最合适的落地方案是：

- 将 `README.md` 重构为“你本人优先”的个人主页
- 使用 GitHub GraphQL API 获取真实贡献数据
- 通过 GitHub Actions 每天自动生成 `assets/heatmap.svg`
- 在不伪造数据的前提下，让展示层保持持续更新

这是在“品牌感、真实性、自动化、低维护成本”之间最平衡的方案。
